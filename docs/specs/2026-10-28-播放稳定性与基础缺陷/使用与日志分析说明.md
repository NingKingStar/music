# 本地诊断日志使用与分析说明

本文说明本轮“本地记录＋主动导出”方案。实际实现、测试及安装包状态见后续交付记录，不能仅凭本文判断已通过手机验收。

## 给测试员的操作步骤

1. 核对诊断包版本及安装兼容性，保留现有应用数据。不同签名不能直接覆盖安装时，先反馈，不要自行卸载原应用。
2. 安装可用诊断包后正常使用。基础诊断默认记录，不要求手机一直连接电脑，也不要求持续打开调试工具。
3. 如果遇到加载慢或突然切下一首，记下大致时间和正在操作的内容；无需自己判断是网络还是音源问题。
4. 在设置页的“播放”卡片选择“导出播放诊断”，在系统保存界面选择位置并完成保存。默认文件名为 `Muses-播放诊断.zip`，取消保存不会提交任何数据。
5. 将导出的诊断文件与下面的简短描述一并提供给分析人员。日志保存在手机，不会自动上传到服务器。

反馈描述可以使用下面格式：

```text
发生时间：大致到分钟
现象：点击后等待 / 播放中跳歌 / 其他
歌曲：自行填写，方便人工对应
播放了多久后出问题：大致秒数或进度
网络：手机 Wi-Fi / 移动数据 / 不清楚
是否正在与电脑联机：是 / 否；联机软件名称
连接方式：USB / 无线 / 不清楚
是否手动点过下一首、暂停或拖动：说明即可
附件：导出的诊断文件
```

传 APK、投屏、控制手机和共享上网是不同操作。USB 或无线连接不能单独说明音乐请求实际经过哪条网络，描述时保留“不清楚”即可，不需要猜测。

日志空间有上限，出现问题后应尽快导出，避免后续长时间使用覆盖较早事件。若失败后重启过应用，也请说明。原有“复制错误日志”入口仍保留，但优先提供完整诊断导出文件，避免只看到最后一条错误。

## 分析人员的处理顺序

1. 先读取导出包内的 `摘要.txt`，再查看 `diagnostic-0.jsonl` 等结构化文件。核对包版本、运行环境、时间范围及刷新/丢弃/截断说明。计数范围是本次运行时，不能解释为全部历史文件累计数。记录不完整时先标记证据缺口，不能把“没有日志”判断为“没有发生”。
2. 依据反馈时间找到运行和播放会话，按事件序号和单调时间还原过程。跨进程记录分别分析，不能简单比较不同运行的单调时间。先核对 `session_basis`：`user_intent` 是用户发起的意图，`creation_candidate` 是数据源创建时捕获的候选，`unknown` 是未知。候选关联仅保证旧对象在后续打开时不改借新意图，不证明媒体实际播放代次；未知回调不能自动并入最近一次点击。
3. 加载慢时区分脚本初始化、解析与回退、探测、数据源打开和播放器准备，说明哪些阶段真实测得、哪些信息未知。
4. 跳歌时先找推进队列的事件与原因，再向前找读取错误、EOF、恢复动作或用户/外部控制。不能仅凭歌曲时长差直接断定音源截短。
5. 对齐网络状态变化与故障时间。系统默认网络只提供环境线索，实际请求网络未知时不得自行推断。可用音频设备类型不等于实际输出路由，界面前后台不等于系统进程重要性；未知信息保留未知。
6. 形成最小问题记录：版本、会话、具体异常链、期望与实际行为、已排除情况、仍待验证的假设和需要补充的测试。

日志能够提高定位精度，但仍可能需要受控复现和设备验证；接口快慢、状态就绪与实际出声不是同一指标。

## 保留和隐私边界

- 本轮标准为最多 5 个文件、每个最多 2 MiB、最长保留 7 天，后台异步记录；满额后按轮转规则覆盖旧记录。
- 新增诊断导出只收录按允许字段构建的脱敏记录，不直接打包原有可能含原始消息的异常堆栈。
- 不记录音源密钥、完整签名播放链接、原始音源脚本、SSID、设备网络地址、个人文件路径和原始搜索词；歌曲通过匿名标识关联。
- 正常记录、导出或写入失败均不得更改原有播放、恢复、音质及切歌策略。
- 本轮没有服务器接收端、自动上传或远程实时查看能力。分析人员需要取得测试员主动提供的导出文件。

## 角色分工

开发维护生产记录与导出；测试验证事件、隐私、存储及失败隔离；文档维护字段与操作说明；独立验收核对实现和证据。日志分析结论先提交缺陷记录，修复另行确认，不把诊断阶段扩展为顺带修复。
